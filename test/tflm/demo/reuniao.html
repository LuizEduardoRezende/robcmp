O resultado

O mesmo programa, nos dois modos

No modo biblioteca (ai.tflm, o caminho do TCC, que continua funcionando), o usuário embute os bytes do modelo, registra cada kernel (a rotina do TFLM que executa um tipo de operação da rede, como uma convolução) e manipula identificadores numéricos. Na sintaxe nativa, o compilador lê o .tflite e faz tudo isso sozinho. Os dois programas abaixo dão o mesmo resultado.

Modo bibliotecalib_seno.rob

use ai.tflm;
modelo = {0x1c, 0x00, ...};  // 3164 bytes
arena = {0u:3000};
int8 main() {
    r = tflm_create_resolver();
    tflm_add_fully_connected(r); // à mão
    h = tflm_create_model(r, modelo, arena);
    entrada = {1.57};
    tflm_set_values(tflm_input(h, 0), entrada);
    tflm_invoke(h);
    saida = {0.0};
    tflm_get_values(tflm_output(h, 0), saida);
    ...
}

Sintaxe nativanat_seno.rob

m = ai_model("hello_world_float.tflite", 3000);
int8 main() {
    m.input0 = {1.57};
    m.invoke();
    saida = m.output0;  // float[1], vindo do .tflite
    ...
}

// O compilador gera: o modelo como constante,
// a área de trabalho do TFLM, o registro de
// cada kernel que o modelo usa e as chamadas
// à mesma API do modo biblioteca.

O ganho não é só de conveniência. Erros que no modo biblioteca só apareciam com o programa rodando, como um tensor que não existe, um vetor de tamanho errado ou um kernel que falta, agora são erros de compilação, com linha e coluna. E o modelo fica na memória certa: na sintaxe nativa ele vai para a flash, enquanto no modo biblioteca ia também para a RAM, onde o person_detect nem caberia no STM32F407.

Arquitetura

Onde o compilador mudou

O Robcmp processa um programa em fases. A sintaxe nativa foi desenhada para que a gramática da RL já a aceitasse: ai_model(...) é lida como uma chamada de função, m.input0 como um nome com ponto, e m.invoke() como uma chamada de método. Por isso o léxico e a gramática não mudaram. Todo o trabalho está na análise semântica e na geração de código.

fase sem mudançafase com ganchoscódigo novo, separado

Um gancho é um desvio de poucas linhas no código existente: quando a análise encontra um nó que pertence a um modelo, entrega-o à extensão TinyML. Quando não pertence, o compilador segue exatamente como antes. A árvore do programa (AST) é a representação do código depois da análise sintática, e o LLVM IR é a linguagem intermediária que o backend do LLVM transforma em código de máquina para cada processador.

Fora da extensão, o núcleo do compilador ganhou 85 linhas em 11 arquivos, quase todas esses ganchos. Houve uma única correção de comportamento: a inicialização das variáveis globais rodava depois do início do main, defeito que existe também em RL pura e que o modelo global da sintaxe nativa expôs.

Análise semântica e geração de código

Como funciona

O TCC tinha um único nó, o ModelNode, que tratava declaração, entrada, saída, invocação e destruição do modelo. O projeto previa decompô-lo em módulos com uma responsabilidade cada. Ficou assim:

MóduloResponsabilidadeNo programa
TfliteModelLê o .tflite na compilação: tensores, tipos, quantização, kernels, e o que o TFLM não executa—
AiModelDeclaração do modelo: confere os argumentos, gera o modelo e a área de trabalho, e a criação do interpretadorm = ai_model(...)
ModelMemberDiz o que cada nome pontilhado é, consultando o .tflite: tensor, propriedade ou métodom.input0, m.output1.raw
ModelUseOs ganchos: troca o nó que o parser criou pelo nó TinyML certo, ou dá o erro—
TensorWriteEscrita na entrada, inteira ou por elementom.input0 = v
TensorReadLeitura, inteira ou por elementox = m.output0[k]
ModelInvokeA inferência; devolve 0 ou −1m.invoke()
WrapperCallDeclara e chama as funções do wrapper, com as mesmas assinaturas do modo biblioteca—
IntegerConstantValores conhecidos na compilação: tamanho da área de trabalho, índices, tamanhos de vetor—

A destruição do modelo não virou módulo: por decisão da especificação, o modelo é criado uma vez e dura o programa inteiro, como é o comum em firmware.

O caminho de um programa

  1. Declaração. Ao encontrar m = ai_model("seno.tflite", 3000), a análise de tipos troca a chamada pelo nó AiModel, que lê o arquivo. A partir daí o compilador sabe quantos tensores o modelo tem, o tipo e o tamanho de cada um e os kernels de que ele precisa. Se o modelo usar algo que o TFLM não executa, o erro sai aqui.
  2. Uso. Cada nome que começa num modelo é conferido contra o arquivo, e não contra a tabela de símbolos. Por isso m.input1 num modelo de uma entrada dá “o modelo tem 1 tensor de entrada (input0)”, e não “símbolo não encontrado”. Propriedades como m.input0.size viram constantes; leituras, escritas e invoke() viram os nós correspondentes.
  3. Verificação. Tamanho de vetor, índice constante, saída somente leitura, tipo da visão crua e limite de modelos são conferidos na compilação. O que só se sabe na execução, como o tamanho de um vetor recebido por parâmetro, o wrapper confere, e o invoke() seguinte devolve −1.
  4. Geração. O AiModel gera o modelo como constante, que no microcontrolador fica na flash, e a área de trabalho do TFLM (a arena) em RAM. Os dois começam em endereço múltiplo de 16, como o TFLM exige. Gera também uma função que cria o interpretador e registra só os kernels que o arquivo usa. As leituras, escritas e o invoke() viram chamadas à mesma API C do modo biblioteca.

O registro de cada kernel numa função própria permite que o linker descarte os demais. O executável leva só o código das operações que o modelo usa, sem a configuração manual que o TCC exigia.

Esta semana

Revisão de código: o que ela achou

Com a sintaxe nativa completa, o compilador e o wrapper passaram por uma revisão para achar defeitos antes do hardware. Foram 5 defeitos, todos casos de borda que os testes não exercitavam; nenhum vinha da estrutura do código. Cada um foi corrigido com um teste novo que o cobre.

corrigido

Valor fora da faixa caía no extremo oposto

Num modelo quantizado, o valor real é convertido para um inteiro de 8 bits. Um valor muito negativo, ou um infinito vindo de uma divisão por zero, virava o maior código possível em vez do menor. Agora a conversão satura do lado certo.

corrigido
defeito da RL

Índice negativo virava outro elemento

Um índice −1 guardado numa variável de 8 bits chegava ao wrapper como 255, um elemento válido, e a escrita ia para o lugar errado. A causa está na RL base: ao ampliar um inteiro, o Robcmp escolhe entre estender o sinal ou completar com zeros pelo tipo de destino, e não pelo de origem. O defeito ficou registrado e foi contornado na extensão, sem mexer no núcleo.

corrigido

Erro na execução não chegava ao programa

Quando o tamanho de um vetor só é conhecido na execução, o wrapper recusava a cópia, mas ninguém era avisado, e a inferência rodava sobre a entrada antiga. Agora a recusa fica marcada no modelo, e o invoke() seguinte devolve −1 sem rodar.

corrigido

Ler um tensor inteiro usava a pilha

Duas leituras da imagem do person_detect somavam 72 KB na pilha, que no STM32F407 (128 KB de RAM) estouraria sem aviso. Agora cada leitura tem um vetor fixo na memória, que o linker contabiliza e acusa se não couber.

corrigido

Modelos que nunca rodariam passavam na compilação

Para ter certeza, os 119 kernels do wrapper foram verificados um a um, com os testes do próprio TFLM (857 casos, nenhuma falha) e a leitura do código. 115 rodam. Os outros 4 dependem de algo que o wrapper não tem: três precisam de variáveis internas que a aplicação cria, e um é exclusivo de uma NPU da Arm, um acelerador que o STM32F407 não tem. Esses 4, e algumas combinações de tipos que o TFLM só recusa ao rodar, agora são erros de compilação.

Antes da revisão, nesta mesma semana: a especificação da sintaxe passou a compilar inteira, e declarar mais modelos do que o wrapper comporta virou erro de compilação, em vez de falhar calado na execução. Quatro modelos públicos maiores foram testados; o EfficientDet-Lite0 roda, e os outros são recusados com o motivo.

Situação

O que roda e o que ainda não

roda verificado

  • Os 5 modelos do TCC na sintaxe nativa, com saídas idênticas às do modo biblioteca: hello world float e int8, spam, person detect e micro speech.
  • Um modelo de duas entradas e o EfficientDet-Lite0, de 4,6 MB, só na sintaxe nativa.
  • O modo biblioteca ai.tflm: os testes do TCC continuam passando.
  • A suíte de testes inteira, incluindo as assinaturas das funções conferidas para x86 e ARM.
  • Compilação para ARM Cortex-M3, o alvo ARM que o Robcmp já tem. Só compilado, não executado.

falta não feito

  • Nada rodou em hardware ainda.
  • O suporte ao STM32F407: mapa de memória, descrição dos periféricos, TFLM compilado para o Cortex-M4 e o build pelo PlatformIO.
  • As medições de tamanho e de tempo de execução.
  • Pontos menores da revisão, que não impedem nada: o mesmo modelo declarado duas vezes ocupa a flash duas vezes, por exemplo.
  • A conferência de tipos cobre 4 operações, as principais; não cobre todas.
Pauta

Para decidir com o orientador

  1. Como o Robcmp vai gerar código para o STM32F407. O compilador não tem um alvo Cortex-M4. Há dois caminhos:
    • Usar o alvo Cortex-M3 que já existe. O código roda no M4 sem mudar o núcleo, mas as contas com float do programa saem em software, sem usar a FPU (a unidade de ponto flutuante do M4).
    • Acrescentar um alvo Cortex-M4. Usa a FPU, mas é uma mudança, pequena, no núcleo do compilador.
    Sugestão: começar pelo Cortex-M3, medir, e decidir o M4 com os números na mão.
  2. Confirmar três decisões tomadas na revisão: o invoke() devolve −1 sem rodar quando um acesso anterior foi recusado; os vetores de leitura ficam fixos na memória, ocupando RAM o programa inteiro; os kernels que dependem de variáveis internas são recusados, em vez de suportados, porque nenhum modelo usado precisa deles.
  3. Defeitos da RL base. A pesquisa registra e contorna, sem corrigir, os defeitos do compilador que não são do TinyML. Já são vários, como a falta de extensão de sinal nas chamadas a funções C e a ampliação de inteiros achada nesta revisão, cada um registrado com a evidência. Reportá-los aos mantenedores do Robcmp?

Onde o modelo fica no binário

O executável é dividido em seções. .data guarda dados com valor inicial, que num microcontrolador ficam na flash e são copiados para a RAM ao ligar. .rodata guarda dados só de leitura, que ficam só na flash. O passo mostra as seções do mesmo programa nos dois modos e o tamanho do person_detect.

make -s -C test/tflm/demo memoria
Saída esperada

    .data.modelo           3164 bytes      ← RAM e flash
    .bss.arena             3000 bytes
  nat_seno.o
    .rodata.m.tflite       3164 bytes      ← só flash
    .bss.m.arena           3000 bytes

  text       data       bss        programa
  83917      322400     126672     tcc_person_detect

No modo biblioteca, os 315 KB do modelo do person_detect iriam para a RAM, e o STM32F407 tem 192 KB. Na sintaxe nativa, ficam na flash.

Se aparecer “No such file or directory … libtensorflow-microlite.a”, o TFLM ainda não foi compilado nesta máquina: a preparação resolve. Há também make -s -C test/tflm/demo sinal, que mostra um dos defeitos da RL base (a falta de extensão de sinal nas chamadas a funções C), se a discussão chegar lá.
